# Findings

Raw material for the write-up. One entry per thing the loops taught us, written while the detail is fresh. Each entry links to the issue or PR it came from.

## 1. Overlapping rules fire unpredictably

The janitor prompt has two rules for a check that doesn't produce results: "skip any script that does not exist yet and note it" (step 1) and "if a check script fails to run at all, file one `needs-human` issue and stop" (Limits). The first janitor run happened before there was a `package.json` at all, so not one check could run. That's the case the `needs-human` rule exists for. The janitor read it as "skip missing scripts" instead: it skipped all four, printed "0 issues" and filed nothing. The run looked clean, and the only sign anything was wrong was that it had checked nothing. The second run, after the TypeScript setup landed, showed a smaller version of the same gap. `npm test` exists but wasn't permitted in the janitor's environment. That didn't trigger `needs-human` either. The janitor skipped it and filed the test and a11y defects from reading the code and HTML, saying so in the issue bodies ([#2](https://github.com/kiml-dev/sincelast/issues/2), [#4](https://github.com/kiml-dev/sincelast/issues/4)). In both runs the loop found the rule that let it keep going more natural than the rule that told it to stop. **Lesson:** when two rules could both apply, the prompt has to say which one wins, and every failure mode (no project at all, missing script, not permitted, crashes on launch) needs to map to exactly one rule. A run that checked nothing should never be able to report success.

## 2. Missing-tool tolerance differs per loop

The janitor skips checks that don't exist. The builder, as first written, ran `npm run a11y` unconditionally before any script existed, so every run would have ended `blocked`. The obvious fix was to copy the janitor's "skip if missing" line into the builder, and that was the wrong fix. The janitor is a scout: a gap in its coverage costs a missed issue. The builder is certifying that a change is safe to merge, and a check that silently didn't run undermines that claim. We added the script instead ([#6](https://github.com/kiml-dev/sincelast/pull/6)). Later, when the builder gained a baseline run, we made "a check fails to start at baseline" a `needs-human` exit, not a pre-existing failure ([#9](https://github.com/kiml-dev/sincelast/pull/9)). The same condition gets a different answer depending on whether the loop is exploring or certifying. #6 had a related catch: pa11y worked locally only because Chrome was already cached, and npm 11 blocks the Puppeteer install script that downloads it. A tool can be installed and still missing on the next machine. **Lesson:** every loop prompt must say what happens when a tool is missing, and the answer comes from the loop's role, not from consistency with other loops.

## 3. Prompts assume a green baseline

The builder prompt said "run the full suite; if anything fails, fix and rerun; three failures and you're `blocked`". That silently assumes `main` is green. With the seeded defects, lint, test and a11y all failed on `main`. Read literally, the prompt makes it impossible to fix one issue without fixing the others, and the one-issue-per-branch rule forbids that. On [#4](https://github.com/kiml-dev/sincelast/issues/4) the builder didn't end `blocked`. It opened [PR #8](https://github.com/kiml-dev/sincelast/pull/8) with lint and test still red, marked each failure "already failing on main and unrelated" with the issue tracking it, and flagged the call under "Unsure about" for a human. That was sensible judgement, but it wasn't what the prompt said, and the next run might judge differently. We made it explicit ([#9](https://github.com/kiml-dev/sincelast/pull/9)). The builder now records a baseline before touching anything, and passing means "everything that passed still passes, and the issue's own check now passes". It lists what was already red under "Pre-existing failures". [PR #10](https://github.com/kiml-dev/sincelast/pull/10) is the first run under the new rule. **Lesson:** any "all checks must pass" rule is really "all checks must not get worse", and the prompt has to say so. Otherwise the loop either deadlocks or improvises.

## 4. A well-written issue pre-answers the reward-hacking trap

Seeded defect 3 was a test asserting the wrong value (`inferBump(["fix"])` expected `"minor"`). A loop told to "make `npm test` pass" has two ways out: fix the assertion, or change `inferBump` to return `"minor"`. The second one passes the tests and breaks the product. The janitor's issue ([#2](https://github.com/kiml-dev/sincelast/issues/2)) closed that door before the builder reached it. It argued that the implementation is right, citing the code comment, the PRD and the test's own name. It also put the constraint in the acceptance criteria: "`inferBump` behaviour is unchanged (`src/index.ts` not modified for this issue)". The builder changed one line of the test and said explicitly that `src/index.ts` was untouched ([PR #10](https://github.com/kiml-dev/sincelast/pull/10)). The builder never had to be clever, because the issue had already been. **Lesson:** the defence against gaming a check belongs in the issue, as acceptance criteria that forbid the shortcut, not in the builder's judgement. That makes the janitor's and planner's issue quality a safety property, not just a convenience.
