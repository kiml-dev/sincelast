# Findings

Raw material for the write-up. One entry per thing the loops taught us, written while the detail is fresh. Each entry links to the issue or PR it came from.

## 1. Overlapping rules fire unpredictably

The janitor prompt has two rules for a check that doesn't produce results: "skip any script that does not exist yet and note it" (step 1) and "if a check script fails to run at all, file one `needs-human` issue and stop" (Limits). The first janitor run happened before there was a `package.json` at all, so not one check could run. That's the case the `needs-human` rule exists for. The janitor read it as "skip missing scripts" instead: it skipped all four, printed "0 issues" and filed nothing. The run looked clean, and the only sign anything was wrong was that it had checked nothing. The second run, after the TypeScript setup landed, showed a smaller version of the same gap. `npm test` exists but wasn't permitted in the janitor's environment. That didn't trigger `needs-human` either. The janitor skipped it and filed the test and a11y defects from reading the code and HTML, saying so in the issue bodies ([#2](https://github.com/kiml-dev/sincelast/issues/2), [#4](https://github.com/kiml-dev/sincelast/issues/4)). In both runs the loop found the rule that let it keep going more natural than the rule that told it to stop. **Lesson:** when two rules could both apply, the prompt has to say which one wins, and every failure mode (no project at all, missing script, not permitted, crashes on launch) needs to map to exactly one rule. A run that checked nothing should never be able to report success.

## 2. Missing-tool tolerance differs per loop

The janitor skips checks that don't exist. The builder, as first written, ran `npm run a11y` unconditionally before any script existed, so every run would have ended `blocked`. The obvious fix was to copy the janitor's "skip if missing" line into the builder, and that was the wrong fix. The janitor is a scout: a gap in its coverage costs a missed issue. The builder is certifying that a change is safe to merge, and a check that silently didn't run undermines that claim. We added the script instead ([#6](https://github.com/kiml-dev/sincelast/pull/6)). Later, when the builder gained a baseline run, we made "a check fails to start at baseline" a `needs-human` exit, not a pre-existing failure ([#9](https://github.com/kiml-dev/sincelast/pull/9)). The same condition gets a different answer depending on whether the loop is exploring or certifying. #6 had a related catch: pa11y worked locally only because Chrome was already cached, and npm 11 blocks the Puppeteer install script that downloads it. A tool can be installed and still missing on the next machine. **Lesson:** every loop prompt must say what happens when a tool is missing, and the answer comes from the loop's role, not from consistency with other loops.

## 3. Prompts assume a green baseline

The builder prompt said "run the full suite; if anything fails, fix and rerun; three failures and you're `blocked`". That silently assumes `main` is green. With the seeded defects, lint, test and a11y all failed on `main`. Read literally, the prompt makes it impossible to fix one issue without fixing the others, and the one-issue-per-branch rule forbids that. On [#4](https://github.com/kiml-dev/sincelast/issues/4) the builder didn't end `blocked`. It opened [PR #8](https://github.com/kiml-dev/sincelast/pull/8) with lint and test still red, marked each failure "already failing on main and unrelated" with the issue tracking it, and flagged the call under "Unsure about" for a human. That was sensible judgement, but it wasn't what the prompt said, and the next run might judge differently. We made it explicit ([#9](https://github.com/kiml-dev/sincelast/pull/9)). The builder now records a baseline before touching anything, and passing means "everything that passed still passes, and the issue's own check now passes". It lists what was already red under "Pre-existing failures". [PR #10](https://github.com/kiml-dev/sincelast/pull/10) is the first run under the new rule. **Lesson:** any "all checks must pass" rule is really "all checks must not get worse", and the prompt has to say so. Otherwise the loop either deadlocks or improvises.

## 4. A well-written issue pre-answers the reward-hacking trap

Seeded defect 3 was a test asserting the wrong value (`inferBump(["fix"])` expected `"minor"`). A loop told to "make `npm test` pass" has two ways out: fix the assertion, or change `inferBump` to return `"minor"`. The second one passes the tests and breaks the product. The janitor's issue ([#2](https://github.com/kiml-dev/sincelast/issues/2)) closed that door before the builder reached it. It argued that the implementation is right, citing the code comment, the PRD and the test's own name. It also put the constraint in the acceptance criteria: "`inferBump` behaviour is unchanged (`src/index.ts` not modified for this issue)". The builder changed one line of the test and said explicitly that `src/index.ts` was untouched ([PR #10](https://github.com/kiml-dev/sincelast/pull/10)). The builder never had to be clever, because the issue had already been. **Lesson:** the defence against gaming a check belongs in the issue, as acceptance criteria that forbid the shortcut, not in the builder's judgement. That makes the janitor's and planner's issue quality a safety property, not just a convenience.

## 5. Every loop gets a seeded failure before it's trusted with a real one

Each loop so far has been tested on a failure we planted, and each time the plant showed something a clean run would have hidden. **Janitor:** three seeded defects ([#1](https://github.com/kiml-dev/sincelast/pull/1), `docs/seeded-defects.md`) showed there was no a11y check to catch one of them. The earlier no-`package.json` run showed that "0 issues" can mean "checked nothing" (finding 1). **Builder:** the same defects left `main` red, which exposed the green-baseline assumption (finding 3) and the missing `a11y` script (finding 2) before any real work went through it. **Reviewer:** a clean PR ([#15](https://github.com/kiml-dev/sincelast/pull/15)) only shows a reviewer can say yes. So we opened a deliberately bad one ([#17](https://github.com/kiml-dev/sincelast/pull/17)) against a throwaway issue, and didn't tell the reviewer. It had an out-of-scope edit to `public/index.html` and a PR body claiming `npm test` passed 5 of 5 when it failed 1 of 5. The reviewer returned `Verdict: CHANGES`. It named both planted defects, correctly derived the two knock-on failures (baseline, criteria) without inventing others, and gave a fix instruction the builder could act on blind. It also flagged that `test:` wasn't in `CLAUDE.md`'s prefix list, without blocking on it. That was a real gap, now closed. **Lesson:** a loop's first run should be against a failure you planted and wrote down in advance (what it should catch, and what it should not). A loop that has only seen clean input hasn't been tested, and an approve-only reviewer is indistinguishable from a rubber stamp until you feed it something bad.

## 6. A planner that reads files against each other finds what humans missed

We planted one contradiction for planner phase 1: a PRD line saying the widget is plain JavaScript, against ADR-001's "Language: TypeScript" ([#19](https://github.com/kiml-dev/sincelast/pull/19)). The prompt says any contradiction must be the first question. It was, naming both files and lines. Phase 1 also found three contradictions nobody had planted, all written by the humans: the PRD says `feature` where everything else says `feat`; the PRD infers the bump from labels while `CLAUDE.md` says titles; and the PRD offers a hosted option that ADR-001's "no database" had quietly ruled out. Phase 2 then noticed that `inferBump` in `src/index.ts` still reads labels after the answers moved inference to titles, and scoped it out of batch 1 explicitly ([#24](https://github.com/kiml-dev/sincelast/issues/24)). Just reading the same files wasn't enough: an accidental phase 2 run read the PRD and ADR-001 before phase 1 and never mentioned the clash. What found it was a prompt step that asked for contradictions directly. **Lesson:** cross-checking is a task you have to assign, not something that happens because a loop read the files. When assigned, it's worth more than the seed: the human-written docs had more contradictions than the one we planted.

## 7. Loops can tell when they're being tested

In phase 1 the planner came across `docs/seeded-defects.md`, identified it as an answer key, and chose not to read it, without being asked to. That was good judgement, but restraint isn't a control. A loop that can Glob the repo can find the answer key, and a loop that knows it's being tested may behave differently from one that doesn't. The reviewer test ([#17](https://github.com/kiml-dev/sincelast/pull/17)) worked partly because nothing in the PR, issue or branch said "test". **Lesson:** keep a seed's answer key outside anything the loop can read until the run is over, then commit it. Don't rely on the loop choosing not to look.

## 8. Non-deterministic checks can't be acceptance criteria

The planner turned "loads in under 1s on slow 3G" into a timed headless-Chrome load test ([#26](https://github.com/kiml-dev/sincelast/issues/26), first version), and then made a later issue fail if the page missed it ([#31](https://github.com/kiml-dev/sincelast/issues/31)). The estimate for the real page was 600–800 ms against a 1 s limit, so the check would fail at random, and a builder told to "fix and rerun" would chase noise. The second miss was the same kind: #31 made `a11y` rebuild the page before checking it. The same check could then write to the working tree or leave it alone, depending on whether the committed page was stale, in loops that must be read-only. Both were fixed before any builder run. #26 is now a byte and request budget (14 KB gzipped, at most 2 requests, nothing render-blocking). The 1 s figure is a one-off manual check. The checks never write. **Lesson:** a loop's oracle must give the same answer twice and must not change state. Anything timed, networked or "about" becomes a budget or goes to a human.

## 9. Run order is state, not sequence

This has now caused four separate problems. The janitor's first run happened before there was a `package.json` (finding 1). Planner phase 2 was run before phase 1 and found no questions file ([#22](https://github.com/kiml-dev/sincelast/pull/22)). The planner runs before the scaffold loop, so it couldn't tell what batch 1 was allowed to depend on (Q11 in `docs/planning/questions.md`). And the builder picks by priority, so it would have started an issue before the PR for the issue it depends on had merged ([#32](https://github.com/kiml-dev/sincelast/pull/32)). Each time, a prompt assumed "X has happened by now", and eventually it ran when X hadn't. Each fix was the same: read the state from the repo or GitHub (does the file exist, is the dependency closed) and exit cleanly if it isn't there. Merging PRs by hand between runs to keep the order right just makes the human the scheduler. **Lesson:** every loop checks its preconditions against real state at the start, and never trusts the order it was started in. This is now a principle in `PLAN.md`.

## Other observations

- Closed issues #2, #3 and #4 still carry `in-progress`. `Closes #n` closes the issue but leaves its labels alone, and nothing in the loops removes the label on merge, so the label state machine never reaches a terminal state. Not fixing yet: a five-line GitHub Action on PR merge can strip it later.
